### 中风险

1. **调度重复**：未来若直接启用 Codex 任务，可能与现有 launchd 重复运行。
2. **版本漂移**：默认 Python 为 3.14，历史量化环境为 3.13；Node 来自 NVM，长期节点重启后的版本选择需要明确。
3. **缺少统一任务契约**：既有脚本和自动化没有统一的输入、输出、权限、超时、幂等和验收格式。

5. **业务数据治理不足**：CRM、交易状态、EnergyMo 材料和认证线索分布在多个用户目录，缺少权威来源和敏感级别标记。

## 8. 建议的目标控制层

后续目标应形成五层，而不是恢复任一旧系统：

1. **入口层**：用户目标和明确批准。
2. **Codex 控制层**：任务拆解、调度、权限检查和状态管理。
3. **执行适配器层**：本地文件、Git、Lark、EnergyMo、量化只读等独立适配器。
4. **安全与审批层**：只读、外部写入、模拟交易、待确认订单、真实交易分级。
5. **验收与审计层**：结构化输出、差异、退出状态、运行证据和 Git 记录。

launchd 只应承担经批准的底层守护职责，不应与 Codex 同时调度同一业务任务。OpenClaw 应保持历史归档状态。

以下仅为建议，本次未执行：

1. **建立控制入口登记表**：为每个 Codex 自动化、LaunchAgent 和历史启动器记录负责人、状态、权限、触发器、输入、输出和停用方式。

## 10. 本阶段结论

Project X 已具备 Git、Codex、Python、Node、uv、Lark CLI 和仓库 SSH 通道等基础执行条件，但当前仍存在多个历史控制入口、活跃研究自动化、已加载的量化 LaunchAgent、交易执行代码和分散的敏感状态。

因此下一步不应立即恢复或重写业务自动化，而应先建立控制入口登记、权限分级和统一任务契约，再以离线只读任务验证 Codex 控制层。所有修复、暂停、迁移、外部连接和业务执行均留待用户批准后的独立阶段。
